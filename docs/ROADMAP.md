# poibot: план функционала и чеклист

## Context
Бот для сохранения мест интереса (бары, кафе, рестораны). Работает в личке и в группах. MVP: сохранить точку (название*, адрес, фото, геолокация, сайт, описание), посмотреть список, найти рядом (100 м / 250 м / 500 м / 1 км). Архитектура должна заранее учитывать: рейтинг и комментарии (общие для одного места, даже если его добавили разные люди/чаты), шаринг точек между пользователями, публикацию личной точки в группе. Каркас бота уже готов (см. `AGENTS.md`).

Решения (согласованы): общее «место» + личные записи; точка принадлежит владельцу, группы подключаются к ней; поиск haversine + bounding box в SQL; фото как Telegram `file_id`; Spring Boot 3.5.x.

## Ключевые архитектурные решения

### 1. Две сущности: `Place` и `SavedPlace`
- `Place` — «физическое место» (одно заведение в реальности): id, lat/lon (nullable), `display_name`, `address` (берутся из первой записи; нужны для показа кандидатов), `merged_into_id`, `created_at`. К нему крепятся рейтинг и комментарии. Пользователь `Place` не редактирует.
- `SavedPlace` — запись пользователя: `owner_id`, `place_id` (FK, NOT NULL), name*, address, description, website_url, photo_file_id/photo_file_unique_id, lat/lon (собственная копия — по ней идёт поиск «рядом»), `created_at/updated_at`. Название/описание/фото пользователя никогда не затрагиваются привязкой к `Place`.
- Поле `copied_from_id` убрано: оно было нужно только как «откуда скопировано» при шаринге, но связь «это то же место» уже даёт `place_id`. Если потребуется атрибуция («поделился @user») — хранить в `place_share_token.created_by`.

### 2. Как связывать записи разных людей (без разрозненных дублей)
Связывание **выполняется автоматически как шаг сохранения**, а не по необязательной кнопке. Автосклейки «вслепую» нет (в здании может быть несколько заведений), но вопрос пользователю задаётся сам, всякий раз когда есть кандидаты:
1. Если у записи есть геопозиция, при сохранении (шаг `RESOLVE_PLACE`) ищутся `Place` в радиусе ~75 м и ранжируются по схожести названия (нормализация: lowercase, без кавычек и слов «бар/кафе/ресторан», Левенштейн/триграммы в Kotlin) и по адресу.
2. Кандидатов нет — создаётся новый `Place` без вопросов.
3. Есть сильное совпадение (схожесть названия выше порога) — один вопрос с предвыбранным вариантом: «Это *Бар «Хмель»* (20 м, ул. Ленина 5)?» → **[Да, то же место] [Нет, другое]** (один тап).
4. Есть только слабые кандидаты — список кнопок `Хмель · 20 м · ул. Ленина 5`, `…` + **«Другое место»**.
5. Привязка меняет только `place_id` собственной записи; чужие записи не затрагиваются. Пока `Place` не подтверждён пользователем, статистика (рейтинг/комментарии) его не использует.
6. Записи без геопозиции получают собственный `Place` без координат; когда геопозиция добавляется позже (редактирование), шаг `RESOLVE_PLACE` запускается снова. Кнопка «Изменить привязку к месту» в карточке остаётся на случай ошибки; ошибочно созданные дубли сливаются через `merged_into_id`.
7. Дополнительный сильный ключ на будущее: ссылка на карты (Google/Yandex id организации) — автоматическое совпадение.
8. Риск «Хмель ×15» снижается тем, что вопрос обязателен и не требует поиска кнопки; метрика в бэклоге: доля сохранений, где кандидаты были, но выбрали «другое место».

### 3. Видимость: владелец + явный выбор групп
- Запись всегда принадлежит владельцу и **по умолчанию личная**. Публикация в группу — осознанное действие владельца **по каждой точке и по каждой группе**: таблица `saved_place_chat (saved_place_id, chat_id, shared_by, created_at)`. «Перенести личную в группу» = опубликовать (личная остаётся личной); можно снять публикацию в любой момент.
- **Список групп пользователя без /start от каждого участника.** Telegram не отдаёт список чатов человека, но есть нативный механизм: в личке бот показывает reply-кнопку **«➕ Выбрать группу»** (`KeyboardButtonRequestChat`, фильтры `chat_is_channel=false`, `bot_is_member=true`). Telegram сам открывает системный выбор чатов пользователя, где есть бот; выбранный чат приходит боту сервисным сообщением `chat_shared` (с `chat_id`) — членство гарантирует сам Telegram. Итого:
  1. Пользователь один раз выбирает группу кнопкой → пара `(user_id, chat_id)` сохраняется в `user_chat`; дальше группа всегда в его списке «Мои группы» с переключателями публикации (повторный выбор не нужен).
  2. Автоматически добавляется группа, куда пользователь добавил бота (`my_chat_member.from`).
  3. Пассивно (бонус): если пользователь использует команду бота в группе, пара тоже пишется в `user_chat`.
  4. Проверка актуальности перед публикацией и при показе — `getChatMember` (best-effort: гарантированно работает, если бот админ группы; при ошибке запись оставляем). Вышедшие из группы удаляются при следующей успешной проверке.
  5. Бот, выбранный в чате как «не участник» (`bot_is_member`) или удалённый → чат `is_active=false` и скрывается из списка.
- **Экран «Публикация» в карточке точки (в личке):** список групп с переключателями ✅/⬜ (по одной точке). Из списка точек — режим «Выбрать несколько» → выбрать точки → выбрать группы → опубликовать. Снятие — тот же переключатель. В группе публикуется ссылка/карточка точки только по запросу `/places`, лишних уведомлений бот в группу не пишет.
- Шаринг пользователю (этап 3): ссылка-токен `t.me/<bot>?start=sp_<token>` + кнопка «Сохранить себе» → создаётся копия `SavedPlace` с тем же `place_id` (шаг `RESOLVE_PLACE` не нужен: место уже известно). Таблица `place_share_token`.

### 4. Группы: диалоги только в личке, в группе — только чтение (FlowEngine не трогаем)
Решение: точки создаются, редактируются и публикуются **только в личке с ботом** — группа не засоряется служебными сообщениями. `FlowEngine` остаётся привязанным к `user.id` (чат = личка), переделка не нужна.
- **В группе** бот отвечает только на команды чтения, без состояния и без flow-движка, через отдельный сервис (`GroupPlacesService`, шлёт через `TelegramClient`): `/places` (одно сообщение со страницами, пагинация правкой того же сообщения), `/nearby` (бот просит реплаем прислать локацию → радиус кнопками → результат одним сообщением). `/add` и прочие диалоговые команды в группе → короткий ответ с кнопкой-deeplink «Открыть в личке».
- Команды различаются по типу чата: `AbstractCommand.execute` получает `chat` — для не-личных чатов делегирует в групповой обработчик (иначе flow ответит пользователю в личку).
- **Privacy mode** остаётся включённым: команды и реплаи на сообщения бота в группе приходят, остального бот не видит.
- **Какие точки видны в группе** — только те, которые владелец явно опубликовал в этот чат (см. п. 3). По умолчанию все точки личные.
- **Жизненный цикл чата:** `my_chat_member` (бота добавили/удалили/кикнули) → `chat.is_active`; `migrate_to_chat_id` (группа → супергруппа) → обновить `chat.id` и ссылки в `saved_place_chat`/`user_chat`.

### 5. Поиск рядом
- **Один запрос всегда по максимальному радиусу (1 км):** bounding box по `lat/lon` (индекс `(lat, lon)`) + haversine в SQL, возврат всех точек с расстоянием. Разбивка по радиусам 100/250/500/1000 (enum `SearchRadius`) делается в Kotlin (`NearbyResult`: точки выбранного радиуса + накопительные счётчики по радиусам). Лишних запросов при смене радиуса нет — результат можно взять из того же ответа (или перезапросить, если локация устарела).
- **Радиус по умолчанию** хранится в `UserSettings` и подставляется автоматически; пользователь не вынужден выбирать каждый раз. Менять можно в любой момент: в результатах всегда есть кнопка **«Изменить радиус»** (все четыре значения) и кнопки-подсказки ниже; выбранный новым радиус становится значением по умолчанию. В настройках/`/nearby` без локации радиус тоже можно сменить.
- **Результат** показывает точки (с расстоянием, по возрастанию) в выбранном радиусе, затем **сводку по большим радиусам — только числа, без данных точек**, и только для тех радиусов, где реально прибавляются точки:
  - выбран 250 м: 1 точка в списке. Дальше — «🔎 до 500 м ещё +3 (всего 4)», «🔎 до 1 км ещё +2 (всего 6)»; если в 500 м новых точек нет, строку про 500 м не пишем, остаётся только 1 км.
  - выбран 100 м, точек нет: «В радиусе 100 м ничего нет», затем строки по 250/500/1000 м — тоже только те, где счётчик вырос по сравнению с предыдущим уровнем (первая подсказка считается относительно 0).
  - каждая сводная строка — кнопка: нажатие переключает радиус (и сохраняет как новый по умолчанию), показывая точки этого радиуса.
  - если нет точек ни в одном радиусе — «Рядом ничего не найдено».
- Область поиска: в личке — свои записи (позже опция «+ группы, где я состою»); в группе — записи, опубликованные в этот чат. Список — страницами; по кнопке точки — карточка и `SendVenue` (показ на карте).

### 6. Диалог добавления — не последовательный, а «карточка-форма» (flow `ADD_PLACE`)
Порядок заполнения выбирает пользователь:
- `/add` показывает **черновик-карточку** со всеми полями (Название*, Адрес, Геолокация, Фото, Сайт, Описание) и кнопками по каждому полю: нажал → бот просит ввод именно этого поля → вернулся к карточке. Кнопки «Сохранить» (активна, когда заполнено название) и «Отмена».
- **Умный ввод без кнопок:** любое присланное сообщение распознаётся по типу и кладётся в нужное поле: location → геопозиция, photo → фото, venue (название+адрес+координаты сразу) → три поля, URL → сайт, текст → название (если пусто), иначе бот спрашивает «В какое поле записать?» кнопками. Можно сразу переслать боту venue/фото и получить заполненную карточку.
- Нажатие «Сохранить» → при наличии геопозиции шаг `RESOLVE_PLACE` (см. п. 2) → сохранено.
- Редактирование существующей точки использует тот же flow (карточка уже заполнена). Удаление — из карточки с подтверждением.
- Состояние черновика — payload flow (JSON в `flow_state`), поэтому диалог можно бросить и вернуться. Лимиты: название ≤100, описание ≤1000, до 500 точек на пользователя.

## Модель данных (Liquibase, схема `poi_bot`)
Миграции (SQL в `liquibase/mvp/`; после MVP — отдельная папка на задачу, подключаемая в корневой `changelog.xml`): `chat`, `user_chat`, `place` (display_name, address, merged_into_id), `saved_place` (без `copied_from_id`; + индексы `owner_id`, `(lat,lon)`), `saved_place_chat`; этап 3: `place_share_token`; этап 4: `place_rating (place_id,user_id,value 1–5, UNIQUE)`, `place_comment (place_id,user_id,text,created_at)`.
Код: `entity/{Place,SavedPlace,Chat,UserChat,SavedPlaceChat}`, `repository/*` (native query для nearby), `service/{SavedPlaceService,NearbySearchService,ChatService,PublishService,GroupPlacesService,GeoUtils}`, `strategy/flow/{addplace,places,nearby,publish}`, команды `AddCommand`, `PlacesCommand`, `NearbyCommand`, `FlowKeys.{ADD_PLACE,PLACES,NEARBY}`, шаблоны `message/template/<flow>/…{,_ru,_en}.ftl`, ключи i18n.
