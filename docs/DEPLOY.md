# Деплой poibot

Схема такая же, как у `royalguardians`: **push в `master`** → GitHub Actions прогоняет тесты → вычисляет версию → собирает jar и Docker-образ → публикует его в GHCR (`ghcr.io/grabovskyalexey/poi-bot`) → через `appleboy/scp-action` и `appleboy/ssh-action` запускает на сервере `scripts/deploy-poibot.sh` (`docker pull` + `docker run --network host`, без docker compose) → создаются git-тег и GitHub Release.

Файлы:
- `.github/workflows/ci.yml` — сборка и тесты на каждый pull request в `dev` и `master`, на push в `dev`; также вызывается из деплоя.
- `.github/workflows/deploy.yml` — деплой на каждый push в `master` (и ручной запуск).
- `scripts/deploy-poibot.sh` — копируется на сервер при каждом деплое и запускает контейнер.
- `scripts/.env.server.example` — образец файла окружения `~/poibot/.env` на сервере.
- `Dockerfile` — образ из готовой `build/libs/poibot.jar`.

## Ветки и обязательные тесты
Поток работы: `feature/*` → pull request в `dev` → pull request `dev` → `master` → автодеплой.

1. На каждый pull request в `dev` и в `master` запускается CI; его проверка называется **`Build and test`**. Новые коммиты в том же PR отменяют устаревший прогон.
2. Чтобы слияние было **невозможно без зелёных тестов**, эту проверку нужно сделать обязательной в защите веток (это настройка репозитория, из файлов она не задаётся):

   GitHub → Settings → Branches → Add branch ruleset (или Add classic branch protection rule) для `dev` и для `master`:
   - Require a pull request before merging (прямой push в защищённую ветку запрещён);
   - Require status checks to pass before merging → добавить **`Build and test`** (проверка появляется в списке после первого прогона CI на любом PR);
   - Require branches to be up to date before merging — по желанию (тесты пойдут на актуальном коде, но придётся чаще обновлять ветку);
   - Do not allow bypassing the above settings — чтобы правило действовало и для владельца репозитория.

   То же командой (после `gh auth login`, нужны права admin на репозиторий):
   ```bash
   for branch in dev master; do
     gh api -X PUT "repos/GrabovskyAlexey/poi-bot/branches/$branch/protection" --input - <<'EOF'
   {
     "required_status_checks": { "strict": true, "contexts": ["Build and test"] },
     "enforce_admins": true,
     "required_pull_request_reviews": null,
     "restrictions": null
   }
   EOF
   done
   ```
   Защита `master` важна: любой push в неё запускает деплой, а так в `master` можно попасть только через PR с зелёными тестами.
3. Слияние `dev` → `master` — это и есть push в `master`, после него автоматически идёт деплой (тесты в деплое прогоняются ещё раз как страховка).

> Ограничение GitHub: на бесплатном тарифе защита веток и rulesets для **приватных** репозиториев недоступны (нужен Pro/Team). Для публичного репозитория всё работает бесплатно.

## Версионирование
- Версия — тег вида `vX.Y.Z`. На каждый push в `master` берётся последний тег `v*` и увеличивается **patch** (`v0.1.0` → `v0.1.1` …). Самый первый деплой — `v0.1.0`.
- Минорное или мажорное повышение: Actions → **Deploy** → Run workflow → поле `version`, например `v0.2.0` (тег не должен существовать).
- Образ получает два тега: версия (`v0.1.1`) и `latest` (это один и тот же образ). Деплой из GitHub Actions запускает контейнер по тегу версии, чтобы в `docker ps` было видно, что именно развёрнуто; вручную по умолчанию берётся `latest`. Версия приложения попадает в `build-info` и пишется в лог при старте (`poibot version 0.1.1 started`).
- Тег и GitHub Release (с автоматическим списком изменений) создаются **только после успешного деплоя**, поэтому у несработавших версий тегов нет, а повторный запуск для того же коммита не плодит новую версию.
- Деплои идут строго по очереди (`concurrency: deploy`).
- Изменения только в `*.md`, `docs/**` и `.gitignore` деплой не запускают.

## 1. Подготовка сервера (один раз)
Нужен Linux-сервер с Docker. Бот использует long polling, поэтому входящие порты открывать **не нужно**, достаточно исходящего доступа к `api.telegram.org` и `ghcr.io`. Свою БД бот не поднимает: он работает в сети хоста (`--network host`, как остальные контейнеры на сервере) и подключается к существующей PostgreSQL в отдельной схеме `poi_bot`.

**Если `royalguardians` уже деплоится на этот сервер**, SSH-часть готова: используйте того же пользователя и ключ, значения секретов можно взять те же (названия секретов в проектах разные, см. раздел 2). Тогда остаются шаги 1.2 и 1.3.

### 1.1 Пользователь деплоя и SSH-ключ (если ещё нет)
Под root (имя любое):
```bash
adduser --disabled-password --gecos "" deploy
usermod -aG docker deploy
```
Ключ только для деплоя (на своей машине): `ssh-keygen -t ed25519 -f deploy_key -C "deploy" -N ""`. Содержимое `deploy_key.pub` — в `/home/deploy/.ssh/authorized_keys` (каталог `.ssh` — права 700, файл — 600, владелец `deploy`), закрытый `deploy_key` — в секрет GitHub `VPS_SSH_KEY`. Проверьте: `ssh -i deploy_key deploy@<сервер>` и затем `docker ps` (без sudo).

### 1.2 Схема в существующей БД
Бот хранит всё в отдельной схеме `poi_bot` и не трогает чужие данные. Схему задаёт параметр JDBC-URL `?currentSchema=poi_bot`: таблицы бота и служебные таблицы Liquibase (`databasechangelog*`) создаются в ней, а не в `public`.

Схему нужно создать заранее (иначе Liquibase не сможет создать в ней свои служебные таблицы). Под суперпользователем или владельцем БД:
```sql
CREATE SCHEMA IF NOT EXISTS poi_bot;
```
Если бот работает под пользователем, который не владеет БД, выдайте ему право на создание схем (миграция 1 выполняет `CREATE SCHEMA IF NOT EXISTS`, а PostgreSQL проверяет право `CREATE` на базу даже когда схема уже есть):
```sql
GRANT CREATE ON DATABASE <имя_БД> TO <пользователь>;
```
Это право нужно только для первого запуска, потом его можно отозвать. Проверено на PostgreSQL 17: все 14 миграций применяются, таблицы бота и Liquibase создаются только в `poi_bot`, `public` и чужие схемы не затрагиваются.

Можно использовать того же пользователя БД, что и у других сервисов, либо завести отдельного (безопаснее: он не получит доступ к чужим схемам):
```sql
CREATE ROLE poibot LOGIN PASSWORD '<длинный случайный пароль>';
CREATE SCHEMA poi_bot AUTHORIZATION poibot;
GRANT CREATE ON DATABASE <имя_БД> TO poibot;
```
Пароль: `openssl rand -base64 24`.

### 1.3 Файл окружения `~/poibot/.env`
Секреты бота лежат на сервере в файле `.env` рядом со скриптом деплоя, в GitHub и в репозиторий они не попадают. Под пользователем деплоя:
```bash
mkdir -p ~/poibot
# создайте ~/poibot/.env по образцу scripts/.env.server.example
chmod 600 ~/poibot/.env
```
Содержимое (формат `docker --env-file`: `KEY=VALUE` без кавычек и пробелов вокруг `=`):
```
TELEGRAM_BOT_TOKEN=<токен от @BotFather>
TELEGRAM_BOT_NAME=<username бота без @>
PG_URL=jdbc:postgresql://localhost:5432/<имя_БД>?currentSchema=poi_bot
PG_USER=<пользователь БД>
PG_PASSWORD=<пароль пользователя БД>
```
`localhost` здесь работает, потому что контейнер запускается в сети хоста — так же подключаются к БД ваши другие контейнеры. Другой путь к файлу можно задать переменной `ENV_FILE` при ручном запуске скрипта.

Порт самого приложения (actuator) тоже занимает порт сервера: по умолчанию это `127.0.0.1:8091` (снаружи недоступен). Проверьте, что он свободен: `ss -ltnp | grep :8091` (порт 8080 занят у `royalguardians`). Если занят, добавьте в `.env` строку `USE_PORT=<другой порт>`.
### 1.4 Образ из GHCR
Репозиторий публичный, а `Dockerfile` содержит метку `org.opencontainers.image.source`, поэтому пакет `poi-bot` создаётся публичным и **`docker login` на сервере не нужен**. После первой публикации проверьте на странице пакета (GitHub → ваш профиль → Packages → poi-bot), что видимость Public; если нет — Package settings → Change visibility → Public (либо выполните на сервере `docker login ghcr.io` с токеном `read:packages`).
Убедитесь, что сервер видит Telegram: `curl -sS https://api.telegram.org` (ответ 302/404 — нормально) и что включена синхронизация времени (`timedatectl`).

## 2. Настройки GitHub (до первого пуша в `master`)
Первый пуш в `master` сразу запускает деплой, поэтому **сначала** сделайте следующее.

**Secrets** — Settings → Secrets and variables → Actions → New repository secret:

| Секрет | Значение |
|---|---|
| `VPS_SSH_HOST` | адрес сервера |
| `VPS_SSH_PORT` | порт SSH |
| `SSH_USER` | пользователь деплоя |
| `VPS_SSH_KEY` | **закрытый** ключ деплоя целиком, включая строки `-----BEGIN…` и `-----END…` |

Variables не нужны. Токен бота и параметры подключения к БД в GitHub **не хранятся**: они лежат только в `~/poibot/.env` на сервере.

**Environment `production`** — Settings → Environments → New environment → `production`. Job деплоя привязан к этому окружению; если его не создать, GitHub создаст пустое само. Добавьте *Required reviewers* (себя), если хотите подтверждать каждый деплой кнопкой.

**Права токена Actions** — отдельно включать ничего не нужно: нужные права (`packages: write`, `contents: write` для тега и релиза) заданы прямо в `deploy.yml`. В Settings → Actions → General должно быть разрешено выполнение действий (*Allow all actions*, либо разрешены `actions/*`, `gradle/*`, `docker/*`, `appleboy/*`).

**Защита веток** — раздел «Ветки и обязательные тесты» выше (для `dev` и `master`). Для публичного репозитория доступна бесплатно.

**Чек-лист перед первым пушем в `master`:**
- [ ] На сервере есть пользователь деплоя, вход по ключу работает, `docker ps` без sudo;
- [ ] В существующей БД создана схема `poi_bot` (раздел 1.2);
- [ ] `~/poibot/.env` заполнен (токен, имя бота, `PG_URL`, `PG_USER`, `PG_PASSWORD`), порт `USE_PORT` (по умолчанию 8091) свободен;
- [ ] Четыре секрета созданы в GitHub (`VPS_SSH_HOST`, `VPS_SSH_PORT`, `SSH_USER`, `VPS_SSH_KEY`);
- [ ] Локальный экземпляр бота с этим токеном остановлен (или для разработки используется другой токен);
- [ ] CI зелёный на PR `dev` → `master`.

## 3. Настройки бота в @BotFather
- `/setcommands` не нужен: бот сам публикует список команд при старте.
- `/setprivacy` → **Enable** (по умолчанию): в группах бот видит только команды и ответы на свои сообщения, этого достаточно.
- `/setjoingroups` → **Enable**: бота можно добавлять в группы.
- Для надёжной проверки членства в группах бота имеет смысл сделать админом группы (без этого `getChatMember` для других участников не гарантирован).

## 4. Первый деплой
1. Заполните секреты и `~/poibot/.env` (разделы 1–2).
2. Остановите локальный экземпляр бота с тем же токеном: один токен может опрашивать Telegram только из одного места (иначе ошибка 409 Conflict). Для разработки лучше завести отдельного бота.
3. Запушьте в `master`. Дождитесь workflow **Deploy**: `Tests` → `Build, publish and deploy`. Первая версия — `v0.1.0`.
4. Шаг `Run remote deploy` считается успешным, только когда в логе контейнера появилась строка `Registered bot running state is: true`; если бот упал или не запустился за 90 секунд, шаг упадёт и покажет последние строки лога.
5. Проверьте на сервере:
   ```bash
   docker ps --filter name=poibot          # образ с тегом версии, например poi-bot:v0.1.0
   tail -n 50 ~/poibot/logs/bot.log        # миграции Liquibase, "poibot version 0.1.0 started"
   ```
6. В Telegram отправьте боту `/start`, затем `/add`.

## 5. Откат, логи, обслуживание
- Ручной запуск скрипта на сервере. Без аргумента берётся образ `latest`, версию можно указать параметром (откат или повторный деплой):
  ```bash
  bash ~/poibot/scripts/deploy-poibot.sh            # latest
  bash ~/poibot/scripts/deploy-poibot.sh v0.1.3     # конкретная версия, например откат
  ```
  Миграции Liquibase выполняются только вперёд: откат образа на версию со старой схемой возможен, пока новые миграции были обратно совместимыми (добавление таблиц/колонок). Для разрушающих изменений схемы готовьте откат отдельно. Следующий push в `master` снова выкатит новую версию.
- **Логи лежат на хосте** в `~/poibot/logs/` (вне контейнера, файлы принадлежат пользователю деплоя, sudo не нужен; другой каталог — переменная `LOG_DIR` при запуске скрипта). Основной файл — `bot.log`, ротация встроена в приложение: файл до 10 МБ, хранится 14 дней, общий лимит 200 МБ (старые файлы архивируются в `bot.log.<дата>.<n>.gz`).
  ```bash
  tail -f ~/poibot/logs/bot.log                    # смотреть вживую
  tail -n 200 ~/poibot/logs/bot.log                # последние строки
  grep -n "ERROR\|WARN" ~/poibot/logs/bot.log      # ошибки и предупреждения
  less +G ~/poibot/logs/bot.log                    # листать с конца
  zcat ~/poibot/logs/bot.log.*.gz | grep "Failed"  # искать по архивам
  ```
  Те же сообщения попадают и в `docker logs -f poibot`; Docker хранит их с ротацией 3 × 10 МБ. Первая строка после старта содержит версию: `poibot version 0.1.1 started`.
- Перезапуск: `docker restart poibot`. Остановка: `docker stop poibot`.

## 6. Резервные копии БД
БД общая и уже обслуживается вами, поэтому отдельный бэкап бота не нужен, если у вас настроено резервное копирование всей базы: данные бота лежат в схеме `poi_bot` и входят в общий дамп. Если нужен дамп только бота (например, перед рискованной миграцией):
```bash
# БД в docker: подставьте имя контейнера БД, суперпользователя и имя базы
docker exec <контейнер-БД> pg_dump -U <суперпользователь> -n poi_bot <имя_БД> | gzip > ~/backups/poibot-$(date +%F).sql.gz
```
Восстановление проверяйте в отдельной пустой БД, а не поверх рабочей:
```bash
gunzip -c ~/backups/poibot-2026-10-09.sql.gz | docker exec -i <контейнер-БД> psql -U <суперпользователь> <тестовая_БД>
```
Миграции Liquibase хранят историю в таблицах `poi_bot.databasechangelog*`, поэтому дамп схемы целиком сохраняет и её.

## 7. Локальная проверка образа
```bash
./gradlew bootJar -PappVersion=0.0.0-local
docker build -t poibot:local .
```
Чтобы проверить миграции без реального токена, поднимите любой PostgreSQL, создайте схему как в разделе 1.2, запустите образ с поддельным токеном формата `123456:AAAA…` и `PG_URL` на эту БД (в общей docker-сети): миграции пройдут, а затем бот ожидаемо упадёт на `401 Unauthorized` от Telegram.
